# Provider adapter examples

These examples give a coding assistant a starting point for an integration. Each provider has its own `functions/`, an `adapter.json` specification, `tests.mjs`, and a synthetic HAR for each function in `fixtures/`. They illustrate a few routes, not every destination known to work with the provider.

| Provider | Example | Function flow |
|---|---|---|
| [Adyen](adyen/README.md) | Secured Fields and checkout encryption | Capture key, time, and encryption format; encrypt mapped card fields |
| [CyberSource](cybersource/README.md) | Flex Microform 2.12.1 | Capture context; bridge the pinned SDK for session aliases; encrypt the token payload |
| [Stripe](stripe/README.md) | Payment Intent confirmation | Reveal submitted form fields and preserve their surrounding payload |
| [OPPWA](oppwa/README.md) | Checkout form pattern | Reveal PAN and CVV in separate requests |

Bindings determine when functions run: the host, method, and path must match, and the function runs at its configured request or response phase. Each provider guide includes a swimlane diagram marking those trigger points.

The function code comes from the adapter authoring work. The public HARs are authored fixtures generated by [generate-fixtures.py](generate-fixtures.py), not copies of customer captures. They contain public test cards, fake identifiers, and synthetic bodies. Original HARs, live credentials, registered resource IDs, private keys, and broad destination inventories are excluded. Tests generate their own RSA key pair in memory.

The `adapter.json` files use the bundled site-check tool's specification format; JSON is valid YAML. They are not raw API payloads. All bindings start disabled. Review the source, mappings, target environment, and existing bindings before using the [registration workflow](../../skills/vgs-checkout-adapter/references/deploy-adapters.md). These examples do not register anything when tested.

## Run the tests

You need Node.js 20+, Python 3, and Docker. From the repository root, prepare the pinned native Starlarky runtime outside the checkout:

```sh
bash skills/vgs-checkout-adapter/scripts/setup-larky.sh /absolute/private/larky-runtime
node examples/adapters/run-tests.mjs --runtime-dir /absolute/private/larky-runtime
# Or test one provider:
node examples/adapters/run-tests.mjs --runtime-dir /absolute/private/larky-runtime --provider stripe
```

The runner executes the exact `.star` function source. It replaces only unavailable gateway imports and the injected input resolver with [explicit host doubles](testing/host-doubles.star). It checks outputs, reveal arguments, pass-through behavior, missing prerequisites, and cross-request capture state. Containers have networking disabled. Runtime and source hashes, fixture hashes, and results are written to a new private temporary directory for each run.

The pinned native 1.0.0 binary has a known JOSE reflection failure. Native encryption cases are reported as **LIMIT**, not as passing crypto tests. For supplemental JVM encryption tests:

```sh
bash examples/adapters/testing/setup-jvm.sh /absolute/private/larky-runtime
node examples/adapters/run-tests.mjs --runtime-dir /absolute/private/larky-runtime --jvm
```

The JVM setup builds the official, checksum-pinned source in Docker and records dependency hashes. It needs network access during setup. Tests then run offline and verify the recorded runtime hashes. Use `--jvm-platform linux/amd64` if that is the architecture used to build your JVM runtime. The encryption tests independently unwrap the RSA key and authenticate/decrypt AES-GCM output with Node's crypto library. They check PAN/CVC values, expiry preservation, context, and unrelated fields.

To explore a prepared test case in the native REPL, use the `input.star` and `test.star` from its reported result directory:

```sh
docker run --rm -it --platform linux/amd64 --network none \
  --mount type=bind,source=/absolute/private/larky-runtime,target=/runtime,readonly \
  --mount type=bind,source=/absolute/private/test-case,target=/work,readonly \
  debian:bookworm-slim@sha256:734a72b3d6142a71993b4bc580ca01d8ca687f77a2c422d96a961d3376b179bc \
  /runtime/larky-1.0.0-linux
```

At the REPL, enter `:load /work/input.star`, then `:load /work/test.star`. This uses synthetic data and the same host doubles as the test. The runtime's native crypto limitation still applies.

Verify fixture reproducibility with `python3 examples/adapters/generate-fixtures.py --check`. The publication check accepts only the exact seven reviewed synthetic HAR hashes; ordinary HAR files remain blocked.

## What was validated

The initial published suite passed **31 native checks and 6 supplemental JVM encryption checks**. Six corresponding native encryption cases reported the known runtime limitation. See [validation.json](validation.json) for source and fixture hashes and per-case results. The SDK bridge also has a JavaScript check using an authored SDK double; no captured JavaScript is executed.

This establishes local behavior with synthetic data. It does not establish current SDK compatibility, gateway dispatch, host permissions, content-type handling, or merchant acceptance. The JVM setup script is provided for reproducibility; this pass used an existing hash-verified build of the same official source rather than rebuilding its dependencies.

Before enabling a binding, follow the [gateway verification guide](../../skills/vgs-checkout-adapter/references/gateway-verification.md). Start with the [adapter skill](../../skills/vgs-checkout-adapter/SKILL.md) when adapting these examples to a new HAR. Keep that capture private and create new synthetic fixtures before sharing tests.
